# v0.16.0 — Model roles for the GPT-6 era (design)

**Date:** 2026-09-17
**Status:** round 3 (revised after Codex round-1 and round-2 REVISE; see sidecar)
**Supersedes:** the v0.13.0 single-model pin (`gpt-5.5` everywhere)

## Why now

- OpenAI retires `gpt-5.5` on 2026-10-14 (per the Codex model catalog: `upgrade.retirement_at`).
  Every pinned invocation in this plugin will start failing on that date.
- The catalog now offers a clear split: `gpt-6-astra` (most capable, supports `xhigh`/`max`/`ultra`)
  and the `gpt-5.6` family (`sol` — the catalog's named migration target for 5.5, `terra` —
  balanced coding, `luna` — fast/affordable).
- The user wants the pipeline to move faster and to change who does what: **Codex writes the code,
  Claude reviews it**, planning runs on the strongest model at the highest practical effort, and the
  two must still agree (double-SHIP) before anything advances.

## Goals

<<<GOALS>>>
- Goal 1: After this ships, every Codex invocation the plugin makes on a live path (MCP thread,
  `codex exec` implementer, cli-harness reviewer) receives a currently-supported model and effort

- Goal 2: The user can change the model or effort for any role in one place (project config or env)

## Existing primitives reused

  per-block validators (`codex_dispatch`, `mailbox`). The `models` block adds one validator.
- `lib/codex-bridge/sidecar.js` — `role_sessions` (already keyed by role since v0.9.0),
  `getCodexThreadId(sc, role)`, `setCodexThreadId` (accepts any `reason` string — no allowlist
  change needed), `buildReplayContext`; `lib/codex-bridge/thread-recovery.js`
  `composeRecoveryPrompt` / `recoverStaleThread` (deps-injected, so model config is one more dep).
- `agents/dispatchers.json` + `lib/codex-bridge/dispatchers.js` — the forbidden/allowed/preferred
  matrix. Goal 4 is a data change plus one extra rung in the existing B.6 fallback procedure.
- `scripts/codex-exec-with-status.sh` — the durable-status wrapper every implementer dispatch
  already goes through. Goal 1's fail-fast lives here.
- `lib/codex-bridge/cli-harness/adapters/codex.js` — composes `codex` args per `execMode`; gains
  model/effort args from options, nothing else. The caller picks the role by phase (§1).
- `bin/codex-paired-doctor` — pass/warn/fail accumulator with JSON mode. Goal 8 is two more checks.
- `role-routing/resolver.js` chooses **which CLI** serves a reviewer role (availability ladder).
  Model roles choose **which model/effort** that CLI runs. They compose: resolver picks `codex`,
  then the harness passes the flags selected by `modelRoleForPhase(phase)` (§1). Model roles never
  override the resolver.

## Design

### 1. One source of truth: `lib/codex-bridge/models.js`

```js
export const MODEL_ROLE_DEFAULTS = Object.freeze({
  planning:           { model: 'gpt-6-astra', effort: 'xhigh'  },
  review:             { model: 'gpt-6-astra', effort: 'high'   },
  implement:          { model: 'gpt-5.6-sol', effort: 'high'   },
  implement_fallback: { model: 'gpt-6-astra', effort: 'medium' },
});
export const VALID_EFFORTS = ['low', 'medium', 'high', 'xhigh', 'max', 'ultra'];
export const CODEX_CLI_VALIDATED_VERSION = '0.153.4'; // the CLI this release was tested against
const SAFE_TOKEN = /^[A-Za-z0-9._-]+$/;               // model ids + efforts; shell-safe by construction
```

Why Sol: the catalog names `gpt-5.6-sol` as the migration target for `gpt-5.5`
(`upgrade.model`). That is a compatibility argument, not a benchmark; the user can switch to
`gpt-5.6-terra` with one config line (§1 override) if it proves better on their code.

| Role | Used by |
|---|---|
| `planning` | brainstorming (spec draft + revision rounds), writing-plans (plan review **and** its mandatory `reviewer-test` panel), autopilot Phase A (plan-slice + test-list review), systematic-debugging (hypothesis rounds), test-driven-development (test-list review). Also the MCP server pin (default only). Thread: `role_sessions["paired-reviewer"]`. |
| `review` | autopilot Phase C (review-slice) and Phase D (docs-update), subagent-driven-development Step C, post-implementation reviewer/panel dispatches, post-merge review's Codex member. Thread: `role_sessions["execution-reviewer"]`. |
| `implement` | every `codex exec` implementer dispatch: single (first rung), two-disjoint members with `adapter: codex-cli`, hybrid `codex-backend`, Codex-run fix passes (first pass). |
| `implement_fallback` | the second rung of the single-implementer ladder (§4) and the second fix pass (§6) only. |

**Role selection for cli-harness dispatches is by phase, not by transport or reviewer identity.**
`reviewer-turn` / `panel` requests already carry `phase`. `modelRoleForPhase(phase)` maps the phase
names the skills actually send today:

| phase value (as sent) | role |
|---|---|
| `spec-review`, `plan-review`, `pre-dispatch`, `tdd-review`, `hypothesis-review` | `planning` |
| `post-implementation-review`, `post-merge-review`, `merge-review`, `docs-update` | `review` |
| anything else | `review` (cheaper), plus `model_role_warning: "unknown phase <x>"` on the turn record |

The runtime resolves the role once per turn and passes `model` + `reasoningEffort` to the harness.
Tests drive the **real request shapes** the skills construct — writing-plans' `reviewer-test`
panel (`phase: 'tdd-review'`), systematic-debugging's `hypothesis-review`, and a
`post-implementation-review` slice review — through the dispatch boundary and assert the captured
adapter argv carries `xhigh`, `xhigh`, and `high` respectively.

Resolution order (later wins): defaults ← `.codex-paired/project.json` `models` ← env.

```json
// fragment — project.json still requires its existing top-level keys (version, app, live_verification)
{ "models": { "implement": { "model": "gpt-5.6-terra" }, "planning": { "effort": "max" } } }
```

Env: `CODEX_PAIRED_MODEL` / `CODEX_PAIRED_REASONING` (existing README names; apply to all roles)
and per-role `CODEX_PAIRED_MODEL_<ROLE>` / `CODEX_PAIRED_REASONING_<ROLE>` (`ROLE` upper-cased,
e.g. `CODEX_PAIRED_MODEL_IMPLEMENT`, `CODEX_PAIRED_REASONING_IMPLEMENT_FALLBACK`). Per-role env
beats global env. Env values are validated the same way as config values; an invalid value is an
error, not a silent fall-through to the default.

API:

- `resolveModelRoles({ repoRoot?, env? })` → `{ roles, sources }`. `sources[role][field]` ∈
  `default | project | env` (used by `doctor` and `model-roles` to explain overrides — this is the
  only reason it exists). Throws `ModelsConfigError` (`code: 'models-config-malformed'`) on any
  invalid layer; never returns a partially-applied result.
- `validateModelsBlock(block)` → `null | { code: 'models-config-malformed', detail }`. Rejects
  non-object, unknown roles, unknown keys, non-string/empty model, model or effort failing
  `SAFE_TOKEN`, effort outside `VALID_EFFORTS`.
- `codexExecArgs(role, roles)` → `['-m', model, '-c', 'model_reasoning_effort=<effort>']`.
- `mcpCallConfig(role, roles)` → `{ model, config: { model_reasoning_effort } }`.
- `roleForThread(role_sessions_key)` → `'paired-reviewer' → planning`, `'execution-reviewer' →
  review`; unknown → `planning`.

`project-config.js` calls `validateModelsBlock` when `models` is present; when absent the config
object is untouched (resolution happens in `resolveModelRoles`, so layering lives in one place).

### 2. Runtime access for skills (no hand-typed models anywhere)

```
node cli.js model-role  --role <planning|review|implement|implement_fallback> [--repoRoot <r>] [--format json|flags|mcp]
node cli.js model-roles [--repoRoot <r>]        # all roles + sources, JSON
```

- `--format flags` → `-m gpt-5.6-sol -c model_reasoning_effort=high` (tokens are `SAFE_TOKEN`, so
  unquoted shell splitting is safe).
- `--format mcp` → `{"model":"gpt-6-astra","config":{"model_reasoning_effort":"xhigh"}}` — the
  exact object a skill spreads into the `codex` MCP call.
- `--repoRoot` defaults to `process.cwd()`; skills pass the repo root they already track.
- Unknown role or invalid config → exit 2 with a usage/detail message on stderr and **nothing on
  stdout**.

Skills obtain role config by running the CLI in a Bash tool call (Claude always has Bash in these
skills; the harness has `node`). Rule: a skill that cannot obtain the config **stops and reports**
— it never opens a thread or subprocess with a guessed model.

`sidecar-init` defaults `--model` / `--reasoning` from the `planning` role. It also records
`thread_config["paired-reviewer"] = { role: "planning", model, effort, opened_at }` (§5).

### 3. MCP server pin and the per-call rule (revised)

`.claude-plugin/plugin.json` launches `codex mcp-server` with
`-c model="gpt-6-astra" -c model_reasoning_effort="xhigh"` (the `planning` defaults) as a
**safety default only**. Every `codex` (thread-opening) call a skill makes now passes `model` +
`config` obtained from `model-role --format mcp` for the thread's role. That is how a project/env
override reaches the thread (round-1 critique 1). Hand-typed model literals in skills remain
forbidden; the skill-structure test allows the field only when the surrounding text references
`model-role`. The "stale `gpt-5.2` example in the tool schema" hazard text stays.

`codex-reply` has no model/config parameter (documented in `codex-pairing.md`; consistent with the
tool schema visible to Claude in this session). Effort is therefore fixed per thread — which is why
§5 uses two threads instead of changing effort on one.

### 4. Codex writes the code

`agents/dispatchers.json`:

```json
"codex":  { "domains": { "ui": "preferred", "ai-harness": "preferred", "backend": "preferred", "general": "preferred" } },
"sonnet": { "domains": { "ui": "allowed",   "ai-harness": "allowed",   "backend": "allowed",   "general": "allowed"   } }
```

`role-recommendations.json` `implementer.preference` becomes `["codex", "claude"]` with a matching
rationale, so the resolver and the dispatcher registry agree.

**Single-implementer ladder (autopilot Phase B.6 and the interactive driver's Step A):**

```
rung 1  codex @ implement           (gpt-5.6-sol high)
rung 2  codex @ implement_fallback  (gpt-6-astra medium)
rung 3  sonnet subagent
        halt implementer-unavailable
```

- Fallback triggers (unchanged list) move down one rung. `BLOCKED` / `NEEDS_CONTEXT` halt without
  descending. **Clarification of the existing ambiguity:** `codex-background-timeout` and
  `codex-background-task-lost` **halt** (they already say so); they are removed from the "triggers
  fallback" list so the two statements no longer conflict.
- **Configuration failure is terminal.** A status file with `exit_code: 78` (the wrapper's
  `model-role-resolution-failed`, §"Fail-fast flags") halts the run with
  `model-role-resolution-failed` — **no worktree reset, no next rung, no Claude fallback**. B.6's
  trigger list states "exit non-zero **other than 78**". Test: orchestrator response to a 78 status
  file leaves the worktree untouched and appends no `failed-fallback-pending` record.
- Each rung follows the existing fallback procedure (append `failed-fallback-pending`, reset to
  `slice_start_sha`, re-bootstrap, dispatch fresh).
- Each dispatch record gains `model_role`, `model`, `effort` (the effective attempt configuration)
  and `rung` (1..3). `appendImplementDispatch` accepts and persists them; existing records without
  them are valid (back-compat).
- A plan `**Implementer:**` directive means "start the ladder at this rung": `codex` → rung 1,
  `sonnet` → rung 3.
- The interactive driver (`subagent-driven-development` Step A) dispatches through the same
  registry and ladder as autopilot instead of "same as upstream — dispatch a subagent". The
  `execution` skill already routes both drivers through `runSplit`; Step A's prose is updated to
  match.

**Fail-fast flags (Goal 1):** `scripts/codex-exec-with-status.sh` gains
`--model-role <role> [--repo-root <r>]` before the `--` separator. The wrapper resolves the snapshot
via `cli.js model-role --format json`, writes `model_role`/`model`/`effort` into the status file
**before** spawning (so evidence exists even if the orchestrator dies), and inserts
`-m <model> -c model_reasoning_effort=<effort>` **immediately after the `exec` token** of the
wrapped command (after `codex exec`, before any user-supplied flags). If resolution fails the
wrapper writes a status file with `exit_code: 78` (EX_CONFIG), `error: "model-role-resolution-failed"`,
and exits 78 — codex never starts. Both new halt reasons (`model-role-resolution-failed`,
`model-role-conflicting-args`) are **registered** in `halt-envelope.js` as terminal with the resume
hint "fix `.codex-paired/project.json` `models` or the `CODEX_PAIRED_*` env, then re-run" and in
`reviewer-archive.js` as PRESERVE (mailboxes kept), so a halt on them archives cleanly instead of
throwing `unknown-halt-reason` (audited: today it would throw).

**Status-file lifecycle (pre-launch write).** The initial status is explicitly nonterminal:
`{ "state": "started", "exit_code": null, "signal": null, "started_at", "completed_at": null,
"model_role", "model", "effort" }`. Every terminal write (`exit_code` set, or a 78 config error)
**preserves** the snapshot fields — the wrapper re-reads/merges rather than replacing the object.
Readers (`classifyBackgroundStatus` in `hybrid/runner.js`, autopilot's completion handler, the
poller) treat a status with `exit_code: null` as "no terminal status yet": they keep polling only
while the task is known alive, and otherwise fall through to the **existing** task-lost halt
(`codex-background-task-lost` / `hybrid-codex-background-lost`) — a wrapper that dies after the
initial write cannot hide task loss until timeout (audited: today an unfinished status object is
classified transient even with `taskAlive: false`). The orchestrator copies the snapshot into its
dispatch record / `started` event once the status file exists, without resolving again. Tests:
live task + initial status → keep polling; death after initial write → task-lost; terminal write
keeps `model_role`/`model`/`effort`.

The locked invocation in the contract doc and autopilot becomes:

```bash
scripts/codex-exec-with-status.sh <status-file> --model-role implement -- \
  codex exec --skip-git-repo-check -s workspace-write -C <worktree> "<prompt>" </dev/null
```

Rung 2 passes `--model-role implement_fallback`. The orchestrator no longer writes `-m` itself.
**No bypass:** when `--model-role` is given and the wrapped command already contains `-m`,
`--model`, or a `model_reasoning_effort` override, the wrapper writes the 78 status
(`error: "model-role-conflicting-args"`) and exits 78. `--model-role` is mandatory for every
**wrapper-launched** `codex exec` (the skill-structure test rejects a `codex-exec-with-status.sh`
block without it); direct adapter calls receive the resolved model and effort through adapter
options instead (see the ownership table below).

**Other transports (Goal 4, explicit scope):**

**One resolution owner per attempt (Goal 1/7).** A "snapshot" is `{ model_role, model, effort }`
resolved by exactly one owner at the start of a **new** attempt; launch argv and attempt evidence
are both derived from that same object. Which owner depends on the transport:

| Transport | Owner | How the snapshot reaches launch | Where it is recorded |
|---|---|---|---|
| `codex-background-bash` (single-implementer rungs, hybrid `codex-backend`, C0 fix passes) | the wrapper | `--model-role <role>`; the wrapper resolves once, builds argv, and writes `model_role`/`model`/`effort` into the **status file** at start (before spawning) | the orchestrator copies the three fields from the status file into the dispatch record / `started` event; it never resolves them itself for this transport |
| `codex-cli` direct adapter (two-disjoint members, cli-harness reviewers) | the orchestrator/runtime | it calls `resolveModelRoles` once, passes `options.model` / `options.reasoningEffort`; the adapter appends the flags and echoes the final argv in `adapterMeta.args` | the same snapshot object goes on `ImplementerDispatchInput` (`modelRole`, `model`, `effort` — new optional properties in `implementer/types.js`) and on the `started` event; `appendImplementerEventLocked` accepts the three optional fields, existing events stay valid |

Consequences: the wrapper never receives model flags from a caller (so there is nothing to
conflict with), and the direct adapter never re-resolves. A config change between orchestration
and launch cannot produce a recorded/launched mismatch because there is only one resolution per
attempt (test: change project.json after resolution, launch, assert recorded == launched).

**Existing vs new attempts.** Resuming an in-flight attempt (status file present, task still
running, or `in-progress` record) never re-resolves; the recorded snapshot is authoritative and is
what the reconciler/promotion reads. Only a **new** attempt (next rung, next fix pass, a fresh
dispatch after halt) resolves current configuration.

Two-disjoint members use `adapter: codex-cli` (the value the frontmatter parser accepts — the
`adapter: codex` example in writing-plans is a doc bug and is corrected); hybrid `codex-backend`
members use `adapter: codex-background-bash`. Both run at the `implement` role; argv never comes
from the plan's `model:` field for Codex members. Failure handling is unchanged: fan-out aborts
required siblings and hybrid halts, exactly as today. No ladder there in this release (documented
in `docs/execution-model.md`). Hybrid's UI half stays Claude by construction — the user chose that
split explicitly.
- cli-harness `codex` adapter: `options.model` / `options.reasoningEffort` append
  `-m <model> -c model_reasoning_effort=<effort>` in both `reviewer` and `implementer` modes, after
  the mode's base args. Supplying `options.args` together with `options.model`/`reasoningEffort`
  throws (`codex adapter: raw args and model options are mutually exclusive`); `options.args` alone
  is documented as a test-only escape hatch, and no production caller passes it (audited: only
  tests do). The runtime sets model options from `modelRoleForPhase(phase)` (§1).

### 5. Two threads: planning and execution (replaces the round-1 rotation design)

Autopilot returns to Phase A (planning) for every slice, so a one-time rotation would downgrade
later plan reviews (round-1 critique 2). Instead the sidecar holds two named threads:

| `role_sessions` key | Model role | Opened by | Used by |
|---|---|---|---|
| `paired-reviewer` | `planning` | brainstorming (exists today) | spec/plan rounds, Phase A, debugging, TDD |
| `execution-reviewer` | `review` | first execution-phase turn (Phase C / SDD Step C) | Phases C and D, SDD Step C, post-merge Codex member |

`sidecar.thread_config[key] = { role, model, effort, opened_at }` records what each thread actually
runs. `setCodexThreadId` gains an optional `threadConfig` argument that writes this entry in the
same locked save; `initSidecar` writes the planning entry. Recovery and re-seeding read
`thread_config`, never rotation history (round-1 critique 3).

Opening the execution thread (once per feature; idempotent on resume because the key exists):

1. `node cli.js sidecar-replay-context --specPath <spec>` → replay JSON.
2. Seed prompt = `composeSeedPrompt(replay, { reason: 'execution-thread', specPath, planPath, pendingPrompt })`.
   `thread-recovery.js` gains `composeSeedPrompt`; `composeRecoveryPrompt` becomes
   `composeSeedPrompt(replay, { reason: 'session-not-found', ... })` and keeps its output for
   existing tests. The seed **instructs Codex to read the spec and plan files from disk** before
   answering (the replay carries only goals, verdict summaries and contentions — it is not enough on
   its own). System rubric + verdict format are prepended by the caller as for any new thread.
3. `mcp codex` with `model-role --role review --format mcp`.
4. `sidecar-rotate-thread-id --role execution-reviewer --reason execution-thread --threadConfig '{...}'`.

Thread loss on either thread: `recoverStaleThread` takes `role` (already does) and reads
`thread_config[role]` to re-seed at the right model/effort, passing `{ model, config }` to
`codexFn` alongside the prompt. **This is the one exception to §3's "obtain current config from
`model-role`":** a recovered thread must continue at the configuration the lost thread had, so the
same review context is judged at the same depth. A second loss works identically because the
config is read from `thread_config`, not from rotation history. Legacy sidecars without
`thread_config` resolve the key's role through `resolveModelRoles` (project/env applied — not the
built-in defaults) and get the entry written on that rotation. `recoverStaleThread` also takes
`specPath` + `planPath` so the seed can name the files to read.

Resume paths (`/autopilot` no-arg, `/execute` no-arg) open nothing new; they use whichever keys
exist. If the model config changed between sessions, existing threads keep their config (a thread's
model is fixed); the change applies to threads opened afterwards. `sidecar-show` already prints
`thread_config`; `doctor` does not inspect sidecars.

### 6. Claude reviews first, then Codex, both SHIP the same commit

Autopilot Phase C and subagent-driven-development Step C gain **Step C0 — Claude's independent
review**, bounded and ordered:

1. Read the committed diff (`slice_start_sha..HEAD`) in full; run the slice's verification command
   and record it as the `claude` side's `verification` audit for this round, tagged with
   `reviewed_sha: HEAD`.
2. Write a findings list — `blocking[]` and `non_blocking[]`, each `file:line` + one-sentence
   reason, verified against the code before listing.
3. If `blocking[]` is non-empty: run **at most two** fix passes. Fix passes are **not** the §4
   implementation ladder — Phase C runs after integration, in the integration checkout, and the
   slice worktree is already gone. Each fix pass:
   - records `fix_start_sha = HEAD` (checkpoint) on the phase state;
   - dispatches Codex `implement` (first pass) then Codex `implement_fallback` (second pass) via
     `codex exec` in the integration checkout with `-C <repo-root>`, the blocking findings, and the
     `fix(slice:N):` commit convention; in interactive mode the foreground fix path is used instead;
   - **configuration error first:** a status file with `exit_code: 78` halts the run with the
     wrapper's halt reason exactly as in B.6 — no reset, no second pass, no foreground fallback
     (same precedence rule, same registered halt);
   - on any other failed pass (non-zero exit, zero commits, non-conforming commits) resets **to
     `fix_start_sha`**, never to `slice_start_sha` — the implementation and any other integrated
     slices stay intact (test: failed fix → checkpoint reset → original implementation commits still
     present);
   - on success: commit, re-run verification, re-review.
   If blockers remain after the second pass, proceed to step 4 anyway with the remaining blockers
   listed — Codex gets to see and push back on them; the 7-round loop then arbitrates as today.
   Claude may not hold a slice in C0 indefinitely.
4. Send the Codex review prompt with a `## Claude review findings` block (both lists verbatim) and
   the `reviewed_sha`. Codex reviews the same commit and returns its verdict.
5. **Same-commit rule, enforced in one place.** `normalizeAuditEntry` now keeps an optional
   `reviewed_sha` (full 40-hex only — abbreviated SHAs are rejected so comparison with
   `git rev-parse HEAD` is exact). Today the two write paths use two validators
   (`appendRound` → `assertShipAuditsForAppend`; `appendRoundWithAudits` → `assertRoundShipBacked`);
   this release **consolidates them into one** `assertRoundShipBacked(round, audits, { headSha })`
   called by both, which gains the rule for SHIP rounds in code-bearing phases:
   - **Legacy evidence (compatibility exception):** if no audit for the round carries
     `reviewed_sha`, the round is accepted as today.
   - **New evidence:** if any audit for the round carries `reviewed_sha`, the SHA-bearing contract
     applies: every SHIP side's qualifying verification audit must carry one, all must be equal
     (asymmetric omission is rejected naming the side), **and `headSha` is mandatory** — a
     SHA-bearing SHIP round appended without `headSha` is rejected at either boundary, so two
     matching stale SHAs cannot pass by omitting the flag. `headSha` must equal the audits' SHA.
   - **Accepted attempt only:** the verification that satisfies the floor must be the audit whose
     `reviewed_sha` equals `headSha`; an earlier C0 verification at a superseded SHA does not count.
   - CLI: `sidecar-append-round` and `sidecar-append-round-with-audits` accept `--headSha <sha>`;
     skills pass `$(git rev-parse HEAD)` from the reviewed checkout for every `review-slice:*` round.
   Tests exercise missing HEAD, mismatched HEAD, asymmetric evidence, and superseded C0
   verification through **both** append paths.
   Any fix after a Codex verdict starts a new round with fresh verification on both sides.

Anti-yes-man applies both ways: Codex must justify disagreement with Claude's findings the same way
Claude verifies Codex's.

Two-disjoint slices (**scoped exception**): post-merge review dispatches its two-member panel
concurrently (`panel/dispatcher.js` uses `Promise.all`; merger review likewise), so there is no
Claude-first ordering on that route. Both members must still SHIP; the Codex member now runs at the

### 7. Goal 7: identities are immutable, attempts carry effective config

- `member_id` and the `model:` field in `**Implementers:**` are **identity** for Codex members
  (`adapter: codex-cli` / `codex-background-bash`). Frontmatter validation (member id model == `model`
  field) is unchanged, so every existing plan keeps parsing and autopilot's plan-digest check is
  never tripped by this release.
- The **effective** model/effort for a Codex member's attempt is the `implement` role (or the ladder
  rung). It is recorded on the attempt evidence — the single-implementer dispatch record
  (`appendImplementDispatch`: `model_role`, `model`, `effort`, `rung`) or the fan-out/hybrid
  `started` event (`model_role`, `model`, `effort`) — never written back into the plan or the
  member id. Claude-cli / ollama members keep using their `model:` field as today (they are not

### 8. Doctor (Goal 8)

Two new checks, both warn-only (a stale catalog must never block a working install):

`models`
- Resolve roles via `node cli.js model-roles` (config error → **FAIL** with the detail: a malformed
  `models` block would stop every skill, so it is the one failing case).
- Catalog at `$CODEX_HOME/models_cache.json` (default `~/.codex/models_cache.json`), schema as
  observed: `{ fetched_at, client_version, models: [{ slug, supported_reasoning_levels: [{ effort }],
  upgrade: { retirement_at } | null }] }`.
  - Absent → pass "catalog not cached; model checks skipped".
  - Unreadable / unparsable / no `models[]` → **WARN** "catalog unreadable".
  - `fetched_at` older than 7 days → **WARN** with the age (checks below still run).
  - Per distinct configured model: **WARN** if slug absent; **WARN** with the date if
    `upgrade.retirement_at` is set; **WARN** if the role's effort is not among that model's
    `supported_reasoning_levels[].effort`.
  - Note in the detail that catalog presence is not proof of account access.
- Output lists each role as `role: model effort (source)` using `sources`.

`codex-transport`
- `codex --version` < `CODEX_CLI_VALIDATED_VERSION` → **WARN** "older than the version v0.16.0 was
  validated against".
- `codex mcp-server --help` exits non-zero → **WARN** "this Codex build does not offer the MCP
  server transport the plugin uses; pin an older Codex or wait for a plugin release that moves
  transports". (The installed 0.153.4 still ships it; upstream docs signal deprecation. This is a
  probe and a statement of compatibility, not a transport rewrite.)
